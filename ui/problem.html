Overview

The problem

Enterprises approve an architecture once, then change it through thousands of pull requests that no one reviews for architectural intent. Tests, security scanners and IaC checks each guard a narrow concern — none answer "does this change still match the architecture we approved?"

Review is manual

Architects compare designs against standards spread across docs and memory. Slow, subjective, gated by a few senior people — so most changes are never reviewed for architecture.

Reviewed only at inception

Sign-off happens once, at kickoff. Hundreds of later PRs change dependencies, topology and ownership. Approval is a snapshot, not proof the delivered system still follows the design.

No continuous review

Tests, security and IaC run on every PR; architecture doesn't. "Services must not share a database" is clear to people but invisible to the build, so drift accumulates silently.

Developers can't self-check

There's no automated way to test a change against the effective org + domain + team + service rules. Teams interpret guidance differently and make locally convenient choices that couple the system.

AI writes and reviews the code

Agents open PRs faster than people can read them, and AI reviewers approve those same changes. When author and reviewer are both models, nothing independently verifies the change preserves boundaries or design.

Why now

The faster code is generated, the more it matters that something reproducible checks its shape. A deterministic, independent architecture check on every PR becomes the missing control.

What the developer feels

  • Rules are tribal knowledge — you learn a boundary exists when a reviewer objects, days later.
  • No fast "am I allowed to do this?" answer before writing the code.
  • Feedback is late and manual; a PR waits hours or days for an architect.
  • Rework is a redesign, not a tweak — objections arrive after implementation.
  • Two reviewers (or two AI runs) give different answers, so the rule feels arbitrary.
  • Merged today, reverted later when a sweep or incident forces a rollback.

A concrete scenario

Checkout keeps Payments available when Customer Profile is degraded: profile data arrives through an event-fed local projection.

A developer needs one more profile field and adds a direct synchronous API call. It compiles, passes unit tests, passes security scanning, and looks fine in review.

It also puts Customer Profile in the revenue-critical path — its next slowdown now stops checkout, and Payments can no longer deploy independently. Not a bug or a vulnerability: a violated architecture decision, usually found only in a later incident.

Root cause: architecture intent (ADRs, diagrams, policies) is disconnected from delivery evidence (code, IaC, config) by slow, manual, lossy links. The cheapest place to catch a violation is the pull request — every later stage multiplies the cost.
