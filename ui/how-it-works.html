How it works

Define → Automate → Enforce

The whole idea in three steps. Writing a rule stays as easy as writing a sentence; enforcing it becomes automatic and repeatable.

1
Define

An architect writes the rule in plain English — via a Markdown pull request or the UI. No DSL, no special syntax. Anyone who can describe the constraint can author it.

2
Automate

An LLM compiles that sentence — once, at authoring time — into an architectural fitness function: a deterministic predicate with generated test fixtures, reviewed by a human like any other change.

3
Enforce

The pipeline replays that fitness function on every pull request. Findings carry a policy ID and file:line. High-confidence drift blocks the merge.

Why this matters now

More and more pull requests are opened, reviewed and merged by AI agents with no human reading the diff. Agents are great at local correctness and blind to the architecture they can't see. A deterministic gate is what keeps an autonomous change from crossing a boundary, sharing a datastore, or turning an async contract into a synchronous one.

The model proposes. The compiled rule decides.

The only place a language model runs is step 2 — turning English into a predicate, under human review. At gate time there is no model in the decision path, so the same pull request always gets the same verdict. That is what makes the check trustworthy enough to block a merge.
